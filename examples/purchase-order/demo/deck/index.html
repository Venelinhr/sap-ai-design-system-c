0. How it started

The team was shipping faster with LLM-assisted UI, but outputs drifted: pseudo-SAP markup, mixed libraries, and Figma screenshots pasted into prompts without a machine-verifiable contract. We needed a design system that an agent can read the same way a senior SAPUI5 developer does: from API metadata, not from vibes.

We paired official SAPUI5 API knowledge (namespaces, aggregations, themes) with a small canonical schema and validators so “generate a PO form” is a testable recipe, not a one-off chat.

1. The issue

  • Unreadable to agents: Figma is visual truth for humans, not a complete control contract for code generation.
  • False confidence: XML that “looks Fiori” but uses wrong default namespaces, missing sap.m.App + Page, or invalid form aggregations.
  • No single pipeline: every developer had a different prompt, different “SAP-like” component set, and no shared regression test.
  • Theme & density drift: without pinning sap_horizon and compact mode, side-by-sides with real SAP apps were unfair.

2. Main goal

Make the SAP design system (SAPUI5 + Fiori patterns) semantically legible and enforceable for LLM agents: a registry + tools + live demos so generation and review use the same source-backed facts, and bad XML cannot pass the build.

Out of scope (deliberate) Replacing Figma. In scope Signals from Figma (tokens, common patterns) layered on a SAPUI5 metadata registry, plus strict view validation and runnable SAP-only UIs.

3. What we manage to hit the goal

Artifacts

  • ComponentSpec JSON Schema and data/registry.json (normalized metadata).
  • Extractors and seed workflow for SAPUI5 docs; data/top_components_seed.yaml for the “top 20” controls to demo first.
  • Figma signals in YAML — tokens and patterns, not a full Figma-to-code compiler.
  • API / scripts for deterministic retrieval and validation (FastAPI, Python scripts).
  • Two SAP-only demos — PO form (sap.m.App + Page) and enterprise sap.uxap.ObjectPageLayout showcase.

People process

  • One golden command before any stakeholder demo: make build-sap-po.
  • One team test protocol (see section 15) so everyone exercises ports 8085 and 8087 the same way.
  • Publish: follow docs/GITHUB_PUBLISH.md for a clean repo others can clone and run.

4. Stages — problem → design → build → learn

4.1 Problem discovery

Catalog failure modes: invalid namespaces, missing shell controls, unbound fragments, and LLM “inventing” properties.

4.2 Design

Lock a schema, define ComponentSpec, map SAPUI5 types to registry entries, define Figma signal slots (tokens, density).

4.3 Build

Implement extractors, validators, demos, and Makefile targets. Pin theme and full-viewport layout patterns.

4.4 Learn (wrong turns → corrections)

See section 7 — each wrong turn fed a new rule or a new check so it does not regress.

5. How the problem is solved (architecture)

  • Layer 1 — SAPUI5 truth: official API names, control modules, aggregations, associations.
  • Layer 2 — Project truth: ComponentSpec + registry + validation scripts in CI.
  • Layer 3 — Design intent: Figma Design Demo Kit + YAML signals (spacing, label patterns) — never contradict Layer 1.
  • Layer 4 — Demos: static OpenUI5 bootstraps from ui5.sap.com with the same rules the validators enforce.

6. Wrong turns (and what we do instead)

  • React-first “SAP look” — rejected for the SAP story; we keep a React sample only for contrast. SAP demos are SAPUI5 only.
  • Bare Page in a static index.html — caused viewport clipping; we standardized on sap.m.App → Page (PO) or ObjectPageLayout (showcase) and fixed #content to full viewport.
  • Treating Figma as executable spec — wrong; we use Figma for signals, SAPUI5 API for fact.
  • Soft validation — “looks OK in browser” — replaced with make build-sap-po and make all gates.
  • Unprefixed ObjectPage in XML with default sap.m — fails at runtime; we default xmlns="sap.uxap" in the Object Page view and prefix sap.m with m:.
  • Dialog without fragment wiring — byId("confirmDialog") from a fragment is brittle; we load with sap.ui.xmlfragment(viewId, ...), addDependent, and keep a control reference.

7. “He wrote directions” — operational rules

  1. Never ship a stakeholder demo with a failing make build-sap-po.
  2. Prefer one documented path in examples/purchase-order/DEMO-INSTRUCTIONS.md over ad-hoc README sprawl.
  3. When a control is in the “top 20” list, the enterprise showcase (8087) must exercise it in real XML, not a comment.
  4. If you change namespaces in a view, run validators — the build is the teacher.
  5. For GitHub: include .gitignore, LICENSE, and publish steps so others can mass-clone and run the same Make targets.

11. What “LLM-readable” means here

  • Deterministic names — library names, modules, and XML tag prefixes match API docs.
  • Retrievable facts — registry and schema so agents fetch “what to instantiate” and “valid children,” not guess.
  • Testable output — generated views must pass the same validators as hand-written ones.
  • Visible proof — demos render with the real SAP theme from CDN, not a CSS skin.

15. Team test protocol (everyone — same order)

  1. Clone repo, python3 -m pip install -e ".[dev]".
  2. Run make build-sap-po — must be exit 0.
  3. Terminal A: make demo-ui5 → localhost:8085 — scroll inside page, no clipped shell — Save shows toast.
  4. Terminal B: make demo-showcase → localhost:8087 — object page sections load; Open review… opens dialog; Close returns; Add line appends a row.
  5. Terminal C: make demo-deck — confirm this page scrolls and links work while 8085/8087 are up.
  6. Optional: make all before merge.

If a port is refused, nothing is “wrong with SAP” — start the matching make demo-* and retry.

16. GitHub for mass usage

17. Industry pattern: “LLM-readable” design system (Pandya)

We apply the same principles as Expose your design system to LLMs (Hardik Pandya): session-start specs, a closed token layer, automated audit, and drift awareness — adapted to SAPUI5 + Fiori (API registry + theme) instead of hand-written React tokens.css for every app screen.
