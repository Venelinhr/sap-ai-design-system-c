Same business fields — different platform contract

This static page is for learning. The official truth for control names, aggregations, and properties is the SAPUI5 API. Read DESIGN.md and SAPUI5-COMPONENTS.md in the repository before building production UI.

Why this comparison exists

  • React (below) uses DOM <input>, <label> — fine for a generic web app or design prototype.
  • OpenUI5 / Fiori uses sap.m.Input, form.SimpleForm, sap_horizon + sapUiSizeCompact for SAP-consistent semantics, density, and a11y in SAP cockpits.
  • An LLM must not emit React controls inside a *.view.xml file — the runtime is sap-ui-core, not React.

Fiori XML (illustrative fragment)

Valid control IDs from API — form.SimpleForm, sap.m.Label, sap.m.Input

<form:SimpleForm editable="true" layout="ColumnLayout" ...>
  <m:Label text="PO Number" />
  <m:Input value="{/poNumber}" change="onChange" />
  <m:Label text="Supplier" />
  <m:Input value="{/supplier}" change="onChange" />
</form:SimpleForm>

Right when: the app is bootstrapped with sap-ui-core.js and Fiori patterns — our SAP demos use this path.

JSON: how the registry helps the LLM (concept)

A ComponentSpec entry names id: "sap.m.Input", lists props and slots (aggregations) so retrieval can inject only valid facts. Compare with schemas/component_spec.schema.json in the repo. 

{
  "id": "sap.m.Input",
  "slots": [ ... ],
  "props": [ { "name": "value", "type": "string" } ]
}
