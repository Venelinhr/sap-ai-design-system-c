Program story (one paragraph)

This program is an end-to-end, LLM-readable design system for SAP Fiori / OpenUI5: it turns API-aligned metadata plus light Figma signals into a queryable ComponentSpec registry, a FastAPI layer for search and validateUiPlan, YAML recipes (object page, list report, and similar), local Fiori demos on fixed ports, CI and governance (including static HTML token rules), and documentation so people and agents stop guessing sap.m and sap.uxap aggregations and can prove correctness with make, schema validation, and browser checks.

Typical stakeholder path: skim README and DESIGN, read the 2-page LLM-READABLE-ADDENDUM for an org handoff, use CASE_STUDY.md as the full map, then go deep in LLM_HUMAN_PLAYBOOK. Shorter “program paths” on paper: WORKFLOW_ZERO_TO_100 (phases), DEMOS_LOCALHOST_8087_8088 (showcase vs subscription), TURNING_POINT_MOMENTUM (when delivery becomes grounded), PLAYBOOK_INDEX (navigation).

Architecture — four layers of truth + data flow

From DESIGN.md: none of the rows below replace Fiori guidelines or the official API; they work together. Runtime XML must match the pinned OpenUI5 version; the registry helps agents retrieve and validate plans, not override SAP semantics.

Layer Authority (what you use it for)
Fiori (human) When to use a pattern, which density, accessibility intent — product and UX judgment.
OpenUI5 / SAPUI5 API What is legal in XML for the pinned version: real namespaces, valid aggregations, real child types, real properties.
ComponentSpec + registry.json Machine retrieval and validateUiPlan: an auditable, queryable layer agents use instead of inventing control names.
data/figma/signals.yaml (Figma sidecar) Semantic hints for variants and design intent; not a second source of truth for aggregations the API defines.

How pieces connect (pipeline)

  1. Input: SAPUI5 API fixtures or a live doc pull is converted to ComponentSpec documents.
  2. Merge: optional Figma semantics are applied to registry or patterns, without overriding API legality.
  3. Store: data/registry.json is validated against the JSON Schema.
  4. Serve: FastAPI exposes search, getComponentSpec, getCompositionRules, getExamples, validateUiPlan, etc.
  5. Generate and check: recipes, PO validation, SAP demo validation, and make token-audit on static non-UI5 pages.
  6. Prove: local OpenUI5 apps in examples/ on the documented ports.

Build a SAP Fiori / OpenUI5 application — summary, instructions, and what to follow

Summary. In this repository, a ship-quality “SAP application” means a running OpenUI5 app in the browser whose view.xml uses only controls and aggregations that exist in the official SAPUI5 API for the same UI5 version you pinned in index.html, follows a credible Fiori pattern (e.g. object page, worklist) with Horizon and compact where the demos do, and can pass make validation and a review that asks “which control and which aggregation is this line?” It is not a static mockup, React in SAP clothing, or Figma names pasted as sap.m class names. Use the registry and API to ground LLM or hand-written XML, then prove the app with a local server and the gates below.

What to follow (order of authority — do not skip)

Every time you add or change UI, use sources in this order. Later layers never override the OpenUI5 API for “what is legal in XML.”

  1. Fiori / UX — When to use a pattern, density, and accessibility intent (guidelines + product judgment). See DESIGN.md for how this maps in-repo.
  2. OpenUI5 / SAPUI5 API (pinned version) — What is valid: namespaces, control names, properties, child types, and aggregations. Bookmark the SAPUI5 API for the version in your index.html bootstrap.
  3. ComponentSpec + registry.json + FastAPI — retrieval and validateUiPlan so agents and humans don’t invent control IDs. Run make run-api and use search / getComponentSpec (or project MCP tools) with small JSON slices, not the whole registry in a prompt. Schema: schemas/component_spec.schema.json.
  4. YAML recipes in recipes/ — object page, list-report, dashboard, etc., as prompt-friendly templates aligned with the registry.
  5. data/figma/signals.yaml — semantic hints only; it does not override API aggregations. Read FIGMA_VS_MACHINE_TRUTH.md before arguing with XML.
  6. Repository rules — AGENTS.md (session + static token rules for non-UI5 pages) and GOVERNANCE.md (merge bar and registry workflow).

How to do it (step-by-step in this program)

This is the execution sequence aligned with WORKFLOW_ZERO_TO_100.md and the phase map on this page. Adjust ports if your Makefile target differs.

  1. Environment. Clone the repo, create a venv, run pip install -e ".[dev]" (as in README.md). Read DESIGN.md and AGENTS.md before generating UI.
  2. Pin UI5 and one pattern. Set the same OpenUI5 version in your app’s index.html (or bootstrap) that you will use in the API docs (e.g. sap_horizon + sapUiSizeCompact to match existing demos). Choose a Fiori pattern: object page, list report, or worklist—match a recipe when one exists.
  3. Machine facts, small batches. With make run-api (port 8000), call search / getComponentSpec (or your MCP tool) to pull 2–3 ComponentSpec objects per feature. Do not paste all of data/registry.json into a chat. Optionally run validateUiPlan on a plan JSON before writing full views.
  4. Write view.xml and controller. Use only real sap.m / sap.uxap (etc.) class names; wire aggregations the API allows (e.g. OPL headerTitle, blocks). Controllers: wire models, formatters, and i18n—avoid huge “fix layout in JS” dumps.
  5. Run the right make demo-*. For the purchase-order OpenUI5 path: make demo-ui5 (8085). For the showcase: make demo-showcase (8087). For subscription: make demo-subscription (8088). Keep the terminal open; fix layout structure (OPL blocks, forms, toolbars) before one-off CSS hacks.
  6. Validate before “done”. At minimum for your path: make build-registry && make validate-registry if you touch the registry; make validate-sap-demo for the PO demo path; run through the 7-step LLM validation and design review checklist on the main view.xml lines.
  7. CI-shaped gate. From the repo root, make all (or the subset in GOVERNANCE.md for your change) so lint, tests, registry, PO/SAP checks, and make token-audit (for static non-UI5 areas) are green. Document any Figma–API tradeoff with API winning at runtime.

What to avoid (common failure modes)

  • Inventing or “remembering” control names — always check the API or registry.json for the exact id.
  • Using a second UI5 version in chat or registry than the one in the browser index.html.
  • Pasting Figma layer names or HTML/React props into view.xml without API verification.
  • Optimizing CSS before OPL blocks / form structure / toolbar layout are correct.
  • Shipping without running at least one make validate-* that applies to the changed path.

Zero → 100% (phases at a glance)

Full narrative and “wrong vs best” prompt patterns: WORKFLOW_ZERO_TO_100.md — the list below is the substance in brief.

  1. 0–20%: Pin the UI5 version; read DESIGN.md and the API for the pattern — not Figma control names as class names.
  2. 20–40%: Use a recipe + ComponentSpec via MCP/HTTP or small JSON slices — not dumping all of registry.json into a prompt.
  3. 40–60%: view.xml and controller: only real sap.* and legal aggregations.
  4. 60–80%: Run make demo-*; fix structure (OPL blocks, forms) before ad hoc CSS.
  5. 80–95%: make validate-*, the 7-step checklist, and line-level “which control and which aggregation?” on XML.
  6. 95–100%: Stakeholder-ready; Figma–API disagreements are documented with API winning for runtime behavior.

Make targets (from repo root — what they do)

  • make demo-playbook-site — runs scripts/serve_playbook_case_study.py on 127.0.0.1, first free port from 8089 (or PLAYBOOK_SITE_PORT), opens a browser unless --no-open.
  • make install — pip install -e ".[dev]" (tests and ruff; not the case-study extras).
  • make build-registry / make validate-registry — extract/merge and validate data/registry.json against the JSON Schema.
  • make run-api — FastAPI on 8000 with /health and component endpoints for retrieval and validateUiPlan.
  • make all — lint, registry, tests, PO generation validation, SAP PO demo validation, and make token-audit on static non-UI5 trees.
  • make demo-ui5 — PO shell on 8085; make demo-showcase — 8087; make demo-subscription — 8088.
  • make demo-deck (8083), make demo-pitch (8084), make demo-react (8086) — see Makefile for the exact http.server directories.
  • make playbook-presentation — writes docs/case_study/exports/SAP_LLM_Playbook_Full.pptx.
  • make case-study-artifacts — shorter narrative PPTX/PDF and repository handout MD+PDF (install .[case-study]).
  • make token-audit — fails if raw hex or forbidden px appear outside the closed token file for the audited static areas.

Tip: if 8089 is taken, the script picks the next free port. Set PLAYBOOK_SITE_PORT=8095 to start the search from another base port.
